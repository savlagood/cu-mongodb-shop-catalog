# ShopCatalog

Учебный каталог товаров и оформление заказов на MongoDB. Решение находится в `solution.js`, условие — в `Задание.md`, результаты опытов — в `results/`.

## Запуск через Podman

Нужны Podman и настроенная команда `podman compose`. На macOS, если виртуальная машина остановлена, сначала выполните `podman machine start`.

Из папки проекта:

```sh
podman compose up -d
podman compose --profile tools run --rm lab reset
podman compose --profile tools run --rm lab fixtures
podman compose --profile tools run --rm lab all
```

`reset` восстанавливает исходные данные, `fixtures` показывает их и ожидаемые ответы, `all` запускает все опыты. Чтобы выполнить отдельную часть, замените `all` на `data`, `index`, `purchase` или `failover`. Сценарии сами подготавливают свои данные, поэтому их нужно запускать последовательно. Для сервиса `lab` требуется профиль `--profile tools`.

Остановка стенда:

```sh
podman compose down
```

Команда сохраняет данные в volumes. Для их удаления используется `podman compose down -v`.

Стенд использует образ `docker.io/library/mongo:8.0.30` с MongoDB и `mongosh`. Replica set `hw2rs` состоит из трёх узлов: `m1:27017`, `m2:27017`, `m3:27017`. Основная база — `hw2`, для смены primary — `hw2_failover`. Клиент запускается в той же внутренней сети контейнеров; порты на хост не публикуются, аутентификация и TLS не настроены.

## Модель данных и запросы

Товары хранятся в `products`, заказы — в `orders`. Позиции `items` встроены в заказ, потому что состав одной покупки ограничен и обычно читается целиком. История покупателя хранится отдельными заказами: она растёт со временем, а отдельные документы позволяют выбирать нужный статус, сортировать покупки и ограничивать выдачу.

Поле `items.price` хранит цену единицы товара на момент покупки. Благодаря этому изменение цены в каталоге не меняет стоимость уже оформленного заказа и историческую выручку.

Валидатор `products` работает в режиме `strict/error`: MongoDB проверяет документы при вставке и изменении и отклоняет нарушения схемы. Обязательные поля и типы заданы через `$jsonSchema`; цена должна быть неотрицательным Decimal128, остаток — неотрицательным целым числом. Дополнительно проверяется, что размеры внутри товара не повторяются.

Поиск использует `$elemMatch`, чтобы размер и достаточный остаток относились к одному варианту. Иначе наличие размера L и запаса у размера M могло бы ошибочно сделать товар доступным для покупки L. Запрос возвращает полные товары со всеми вариантами, упорядоченные по `_id`.

История отбирает заказы по `userId` и `status`, сортирует по `{createdAt: -1, _id: 1}` и возвращает не более 20 полных документов. Второе поле сортировки делает порядок однозначным при равных датах. Для строк используется `simple` collation — точное сравнение с учётом регистра.

## Отчёт о продажах

Агрегация учитывает только оплаченные заказы за период `[from, to)`: начало включается, конец исключается. После раскрытия `items` позиции группируются по SKU, поэтому разные размеры одного товара попадают в общий итог. Количество складывается, выручка вычисляется как сумма `qty × items.price` в Decimal128. Названия добавляются из `products` через `$lookup`. В ответ попадают пять товаров с наибольшей выручкой; при равенстве они упорядочены по SKU.

Пример расчёта для товара A за январь 2026 года:

| Заказ | Размер | Количество | Цена единицы | Выручка |
|---|---|---:|---:|---:|
| `sale-start` | M | 2 | 100.00 | 200.00 |
| `sale-middle` | L | 1 | 120.00 | 120.00 |

Итого: **2 + 1 = 3 единицы**, выручка — **2 × 100.00 + 1 × 120.00 = 320.00**. Используются цены из заказов, поэтому изменение текущей цены A в каталоге не влияет на этот расчёт.

## Индекс для истории заказов

Для фильтра и сортировки истории создан индекс:

```js
{userId: 1, status: 1, createdAt: -1, _id: 1}
```

Сначала идут поля, по которым задано равенство, затем — поля сортировки. Это порядок Equality → Sort из правила ESR: внутри выбранного покупателя и статуса записи уже расположены по дате и `_id` в нужных направлениях.

Сравнение `explain("executionStats")` выполнено для `{userId: 2500, status: "paid"}` на одних и тех же 10 000 заказов. До добавления составного индекса был только стандартный `_id_`. `hint` не использовался.

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10 000 | Да |
| После индекса | 20 | 20 | 20 | Нет |

До индекса MongoDB просматривала всю коллекцию (`COLLSCAN`) и отдельно сортировала результат (`SORT`). После — читает подходящий диапазон индекса (`IXSCAN`) и загружает 20 документов (`FETCH`), без отдельной сортировки. Загрузка документов нужна, поскольку возвращается полный заказ. Список `_id` и порядок выдачи до и после совпадают.

Индекс занимает дополнительное место и требует обновления при вставке, удалении и изменении индексируемых полей, увеличивая работу при записи.

## Оформление заказа

Покупка списывает два товара и создаёт заказ в одной многодокументной транзакции и одной сессии. Оболочка `transaction` вызывает `startTransaction()` и передаёт в код покупки базу, связанную с этой сессией. Все чтения и записи выполняются через неё.

Проверка запаса входит в условие `updateOne`: должны совпасть SKU и размер, а остаток должен быть не меньше количества покупки. Списание выполняется через `$inc`. Если товара, размера или достаточного запаса нет, код выбрасывает `ITEM_UNAVAILABLE`. Оболочка вызывает `abortTransaction()`, поэтому отменяется и уже выполненное списание первого товара. После двух успешных списаний вставляется заказ с ценами покупки, текущей датой и статусом `created`; затем оболочка вызывает `commitTransaction()`. Сессия закрывается в `finally`.

Настройки транзакции:

| Настройка | Назначение |
|---|---|
| `readConcern: {level: "snapshot"}` | Чтение согласованного снимка данных. |
| `readPreference: "primary"` | Выполнение операций на primary. |
| `writeConcern: {w: "majority", j: true, wtimeout: 10000}` | Подтверждение commit большинством узлов с журналированием; ожидание write concern ограничено 10 секундами. |

Сессия создаётся с `causalConsistency: true`, чтобы учитывать причинный порядок операций. Ошибка самого commit может означать неопределённый результат; оболочка не выдаёт её за подтверждённый откат.

**Атомарность** гарантирует, что два списания и создание заказа фиксируются вместе либо отменяются. Однако новый вызов покупки — отдельная операция, поэтому от повторного списания нужна дополнительная защита.

Для этого используется `operationId`, записанный в `_id` заказа. В начале покупки код ищет такой заказ и сравнивает `userId` и позиции `sku`, `size`, `qty` в исходном порядке. Если значения совпадают, возвращается сохранённый заказ с прежними датой и ценами, без новых списаний. Другие параметры дают `REQUEST_CONFLICT`. Порядок ключей объекта и текущая цена каталога на сравнение не влияют. Это обеспечивает последовательный повтор уже подтверждённой покупки; полный протокол обработки конкурентных и сетевых повторов в эту реализацию не входит.

## Смена primary

Клиент подключается к списку узлов `m1`, `m2`, `m3` с параметром `replicaSet=hw2rs`. Драйвер отслеживает состав и роли узлов. После `stepDown` и выборов он обнаруживает новый primary и направляет операции туда. Менять адрес вручную или создавать новый экземпляр клиента не требуется; физическое соединение при этом может измениться.

Контрольные записи используют `{w: "majority", j: true}`. Такое подтверждение означает, что запись сохранена большинством узлов, но отдельная secondary ещё может отставать. Поэтому чтение с произвольной secondary не обязано сразу увидеть последнюю запись. Сам по себе `readConcern: majority` также не гарантирует её свежесть. В опыте чтение после переключения идёт с нового primary.

## Шардирование

По условию ключ шардирования — `{userId: 1}`. Диапазон `[2000, 5000)` находится на шарде B, остальные значения — на A.

| Запрос | Куда направляется | Почему |
|---|---|---|
| История `{userId: 2500}` | Только на B | Значение ключа однозначно попадает в диапазон B. |
| Общий отчёт `{status: "paid"}` | На A и B | Условия по ключу шардирования нет, оплаченные заказы могут находиться на обоих шардах. |

Индекс `{status: 1}` внутри шардов не меняет число участников общего отчёта. Он может ускорить локальный поиск оплаченных заказов и сократить просмотр документов, но не меняет карту размещения данных, которой пользуется `mongos`.

## Результаты и использованные материалы

`results/results.json` содержит ответы запросов, проверку валидатора, полные планы, состояния покупок, ошибки, снимки счётчиков транзакций и результаты переключения. Формат Extended JSON сохраняет BSON-типы. Консольный вывод находится в `results/run-all.log`, сведения об окружении — в `results/environment.json`.

Из учебного комплекта использованы контрольные данные, генератор 10 000 заказов, настройка replica set, оболочка транзакции, сбор счётчиков и сценарий смены primary. Решение опирается на материалы недели 4 о документах, массивах, исторических ценах, агрегации и индексах, а также недели 5 о транзакциях, репликации и шардировании.

Окружение адаптировано под Podman: в `compose.yaml` указано полное имя образа, а запуск выполняется через `lab-podman.js` — копию `lab.js` с командами справки для Podman и явным профилем `tools`. Логика сценариев сохранена.
